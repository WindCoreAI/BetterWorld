# Implementation Plan: Cooperative Depth & Governance

**Branch**: `018-cooperative-depth-governance` | **Date**: 2026-02-16 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/018-cooperative-depth-governance/spec.md`

## Summary

Deepen cooperation from institutional to personal, distribute governance power through earned community moderator roles, complete mentorship and learning pathway systems, and add cross-group dynamics. This spec addresses Blueprint Traits 5 (Cooperation), 7 (Mild Hierarchy), plus remaining features from Traits 1, 2, 3, 6, and 8. Builds on Sprint 16 (Social Fabric) and Sprint 17 (Community Identity) foundations.

**Core deliverables**: Mentorship pairing, mission buddies, informal help system, community moderator role, elevated human agency (human-proposed solutions), learning pathways, case study library, cross-group challenges, circle enrichment, cooperative achievements, flexible mission limits, plus 8 remaining enhancements (gratitude narratives, teaching rewards, power distribution audit, agent fingerprint, network health, people discovery, personalized feed, welcome ambassadors).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

**Pre-research check**: PASS (2026-02-16) — All 7 principles evaluated. One complexity justification for Principle V (tier-based mission limits).
**Post-design re-check**: PASS (2026-02-16) — Data model, API contracts, and quickstart reviewed against all principles. No new violations. All guardrail content types documented. All token flows use double-entry pattern. Moderator audit trail is immutable. Buddy/helper reward math preserves economic balance.

### Principle I — Constitutional AI for Good (NON-NEGOTIABLE): PASS

All new user-generated content types in this spec will pass through the existing 3-layer guardrail pipeline:
- **Help messages** (FR-020, max 500 chars): Layer A regex + Layer B classifier before delivery
- **Circle posts** (FR-047): Same guardrail integration pattern as discussion threads (Sprint 16)
- **Gratitude narratives** (FR-056, max 1000 chars): Layer A + Layer B before visible
- **Human-proposed solutions** (FR-027-028): Same guardrail pipeline as agent solutions
- **Case study AI summaries** (FR-039): Generated by Claude Sonnet, still pass Layer A validation
- **Help request notes** (FR-024): Layer A regex check before display
- **Moderator Layer C queue** (FR-016): Moderators review within existing Layer C; their decisions logged as training data per constitution

No bypass paths. All new content enters "pending" state until guardrail evaluation completes.

### Principle II — Security First (NON-NEGOTIABLE): PASS

- **Moderator audit trail** (FR-018): All moderator actions logged with identity, action type, target, decision, timestamp — immutable audit log per constitution requirement
- **Rate limiting**: New write endpoints (help offers, circle posts, mentor ratings, solution proposals) rate-limited per existing patterns
- **Zod validation**: All new API inputs validated with Zod schemas at system boundaries
- **Moderator privilege boundaries** (FR-017): Strict allow-list — moderators cannot resolve disputes, adjust rates, manage flags, or suspend users. Server-side enforcement, not UI-only
- **2-hop exclusion for moderators** (Edge Case): Moderators excluded from reviewing content by their connections
- **Buddy/helper reward flows**: Double-entry accounting with SELECT FOR UPDATE prevents race conditions

### Principle III — Test-Driven Quality Gates (NON-NEGOTIABLE): PASS

- All new services, routes, and workers will have integration tests
- Frontend components with user interaction will have component tests
- Coverage must not decrease from current 1484-test baseline
- TypeScript strict mode zero errors; ESLint zero errors
- New guardrail integrations covered by existing regression suite

### Principle IV — Verified Impact: PASS

- **Mentorship rewards** (FR-004): 2 tokens per mentee mission completion via double-entry with balance_before/balance_after
- **Buddy reward splits** (FR-010): 60/40 split via double-entry — two transactions from mission reward pool
- **Helper reward shares** (FR-023): 25% deducted from claimer's share via double-entry — claimer gets 75%, helper gets 25%
- **Teaching rewards** (FR-058): Double-entry for mentorship completion (5), help interactions (2), case study contributions (2), ambassador welcomes (1)
- **Ambassador rewards** (FR-063): 1 token per welcome, capped 5/month, via double-entry
- **All token operations**: SELECT FOR UPDATE with idempotency keys (replay protection)

### Principle V — Human Agency: REQUIRES COMPLEXITY JUSTIFICATION

- **CONFLICT**: Constitution states "Maximum 3 active missions per human." FR-054 introduces tier-based limits: newcomer=2, contributor=3, advocate=4, leader=5, champion=6.
- **Justification**: See Complexity Tracking below. The hard-coded "3" was a Phase 1 safeguard. Tier-based limits preserve the anti-overcommitment intent while rewarding reliability.
- **Safeguard**: FR-055 reverts limits if completion rate drops below 80%, maintaining the protective principle.
- All other Human Agency requirements preserved: voluntary claiming, atomic SELECT FOR UPDATE SKIP LOCKED, auto-expiry, no penalty for declining.

### Principle VI — Framework Agnostic: PASS (No Impact)

This spec primarily adds human-facing features. Agent API contract unchanged. Human-proposed solutions (FR-027-032) integrate with existing problem/solution API patterns.

### Principle VII — Structured over Free-form: PASS

- All new entities defined with Drizzle schemas and Zod validation
- Help messages, circle posts, and narratives have character limits and type constraints
- Case study summaries follow structured format (context, approach, evidence quality, learnings)
- Moderator actions use enum-based action types
- Agent fingerprint uses structured radar chart data (5 dimensions)
- Power audit uses structured metrics (Gini coefficient, numerical scores)

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Principle V: Tier-based mission limits (2-6) instead of hard-coded 3 | Rewarding reliable participants with increased capacity directly supports cooperative depth — champions who consistently complete missions should be trusted with more. FR-055 safeguard reverts limits if completion rate drops below 80%, preserving the anti-overcommitment protection. | Keeping hard-coded 3 would penalize high-performing participants and conflict with the trust-tier system already in place. The safeguard mechanism ensures the protective intent of the original limit is maintained. |

**Constitution Follow-Up**: After implementation, recommend a constitution v1.1.0 patch to update Principle V from "Maximum 3 active missions per human" to "Tier-based mission limits (2-6) with completion rate safeguard" to match implemented behavior.
