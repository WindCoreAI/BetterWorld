## Goal

Analyze the BetterWorld frontend pages, API routes, auth middleware, and component structure to produce structured Markdown test plans. Each flow plan describes the exact user journey through the application, including prerequisite setup, step-by-step actions, expected outcomes, and API calls involved.

These flow plans serve as the bridge between code understanding and test generation — they're the "test scripts" that `/generate-e2e` will convert into executable Playwright tests.

## Execution Steps

### Step 1: Scan the Codebase

Read the following sources to build a complete map of testable surfaces. Do this once, then reference throughout:

1. **All page files** in `apps/web/src/app/` — identify every route, its auth requirements, and key UI elements
2. **Navigation component** (`apps/web/src/components/Navigation.tsx`) — understand nav structure, auth-dependent links, dropdown groups
3. **API routes index** (`apps/api/src/routes/v1.routes.ts`) — all API endpoints and their route groups
4. **Auth middleware** (`apps/api/src/middleware/humanAuth.ts`) — understand how auth is enforced
5. **Frontend auth** (`apps/web/src/hooks/useHumanAuth.ts`, `apps/web/src/lib/api.ts`) — localStorage token keys (`bw_human_access_token`, `bw_human_refresh_token`), auth state management
6. **Key form components** — RegisterForm, CreateAgentModal, NewThreadForm, EvidenceSubmitForm, etc.
7. **E2E helpers** (`e2e/helpers/`) — understand what utilities are already available for test generation

### Step 2: Generate Flow Files

For each requested flow, write a Markdown file to `e2e/flows/<name>.flow.md` using this exact structure:

```markdown
# <Suite Name> Flow

> Generated by /ux-flows on <date>

## Setup Requirements

- [ ] API server running (port 4000)
- [ ] Web server running (port 3000)
- [ ] PostgreSQL with betterworld database
- [ ] Redis running
- [Specific requirements, e.g., "Registered human with verified email"]

## Test Scenarios

### Scenario 1: <Descriptive Name>

**Pages**: /path/one -> /path/two -> /path/three
**Auth Required**: Yes | No | Mixed
**Prerequisites**: None | "Registered human" | "Active agent" | etc.

**Steps**:
1. Navigate to /path
2. Verify page elements: heading text, buttons, form inputs (include selectors)
3. Fill form: field="value" (include actual field names from components)
4. Click "Button Text"
5. Expect redirect to /next-path OR expect element visible

**Expected Outcomes**:
- Specific assertion: "Page contains heading 'Join BetterWorld'"
- API response: "POST /api/v1/human-auth/register returns {ok: true}"
- State change: "Token stored in localStorage"
- No console errors

**API Calls Involved**:
- METHOD /api/v1/endpoint { requestBody }
- METHOD /api/v1/endpoint -> { responseShape }

**Selectors** (from component source):
- Heading: `h1, h2` or `text=Exact Text`
- Form inputs: `input[type="email"]`, `input[name="password"]`
- Submit button: `button[type="submit"]` or `text=Button Label`
- Content: `text=Expected Text`

---

### Scenario 2: ...
```

## Operating Principles

- **Read before writing**: Always read the actual page component source to get accurate selectors and field names. Never guess.
- **Be specific with selectors**: Include the actual text, ARIA roles, and input names from the source code. Prefer `text=Exact Text` and `role=button[name="Label"]` over CSS classes.
- **Include both happy path and error cases**: Each flow should test what happens when things go right AND when they go wrong.
- **Note auth requirements clearly**: The test generator needs to know which scenarios need authenticated browser sessions.
- **Keep scenarios independent**: Each scenario should be self-contained with its own prerequisites clearly stated.
- **Reference API contracts**: Include the exact API endpoint, method, and expected response shape for backend interactions.
- **Respect existing helpers**: Reference the available helpers in `e2e/helpers/` (auth, data-factory, db, assertions, constants) — the test generator will use these.
